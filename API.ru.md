# Документация API Xcash

В этом документе описаны текущие публичные API-интерфейсы Xcash. Все маршруты Django/DRF API **не содержат `/` на конце**, запрашивайте пути из примеров как есть.

## Адреса шлюзов

### Самостоятельное размещение (Self-hosted)

Если вы выполнили самостоятельное развертывание согласно [README](README.md), адресом API-шлюза будет `SITE_DOMAIN`, настроенный в `.env`:

| Назначение | URL | Описание |
|------|-----|------|
| API-шлюз | `https://{ваш домен}` | Например, `https://{ваш домен}/v1/invoice` |
| Панель администратора | `https://{ваш домен}` | Создание проектов, настройка RPC сетей, настройка Webhook, просмотр записей о счетах и депозитах |

### Официальный сервис Xcash

Если вы используете официальную облачную версию Xcash ([xca.sh](https://xca.sh)), используйте:

| Назначение | URL | Описание |
|------|-----|------|
| API-шлюз | `https://pay.xca.sh` | Например, `https://pay.xca.sh/v1/invoice` |
| Шлюз EPay | `https://pay.xca.sh/epay/submit.php` | Совместимая точка входа EasyPay V1 |
| Консоль SaaS | `https://dash.xca.sh` | Получение AppID / ключа HMAC, настройка проектов |

## Коды сетей и валют

### Коды сетей (Chain Code)

Текущие публичные интерфейсы используют следующие коды сетей:

| Сеть (Chain) | Код (code) | Тип | Токен для газа | Chain ID |
|------|------|------|----------|----------|
| Ethereum | `ethereum` | EVM | `ETH` | `1` |
| BNB Smart Chain | `bsc` | EVM | `BNB` | `56` |
| Polygon PoS | `polygon` | EVM | `POL` | `137` |
| Arbitrum One | `arbitrum-one` | EVM | `ETH` | `42161` |
| Optimism | `optimism` | EVM | `ETH` | `10` |
| Base | `base` | EVM | `ETH` | `8453` |
| Tron | `tron` | Tron | `TRX` | - |
| Sepolia | `sepolia` | EVM Testnet | `ETH` | `11155111` |
| Nile | `nile` | Tron Testnet | `TRX` | - |
| Anvil Local | `anvil` | EVM Local | `ETH` | `31337` |

Тестовые проекты могут использовать только тестовые сети или локальные сети (такие как `sepolia`, `nile`, `anvil`), боевые проекты могут использовать только основные сети (mainnet).

### Символы криптовалют (Crypto Symbol)

В параметре `crypto` используется символ валюты, например `USDT`, `USDC`, `DAI`, `ETH`, `BNB`, `POL`, `TRX`. Фактические доступные комбинации зависят от включенных сетей, валют и смарт-контрактов в админ-панели.

## Механизм аутентификации

За исключением эндпоинтов, явно обозначенных как публичные, все интерфейсы `/v1/*` требуют подписи HMAC-SHA256.

### Учетные данные

После создания проекта в панели администратора система генерирует:

| Поле | Описание |
|------|------|
| `appid` | Уникальный идентификатор проекта, например `XC-A3BK7NMG` |
| `hmac_key` | Ключ HMAC-подписи проекта |

Для прохождения проверки готовности проекта для публичного API необходимо как минимум настроить `Белый список IP (IP 白名单)`, `URL уведомлений (通知地址)`, а также иметь доступный адрес для сбора средств (адрес прямого сбора кошелька или адрес смарт-контракта сбора соответствующего типа сети). Если для какой-либо сети установлен режим сбора через смарт-контракт, то должен быть настроен адрес сбора соответствующего типа сети.

### Заголовки запроса

```http
XC-Appid: {appid}
XC-Timestamp: {unix_timestamp}
XC-Nonce: {unique_nonce}
XC-Signature: {hmac_signature}
Content-Type: application/json
```

| Заголовок | Описание |
|--------|------|
| `XC-Appid` | AppID проекта |
| `XC-Timestamp` | Текущий Unix-таймштамп, в продакшен-среде допускается расхождение с сервером в 300 секунд |
| `XC-Nonce` | Уникальный Nonce, не должен повторяться в течение 300 секунд для одного AppID |
| `XC-Signature` | Подпись HMAC-SHA256 в нижнем регистре (hex) |

### Вычисление подписи

```text
message   = XC-Nonce + XC-Timestamp + request_body
signature = HMAC-SHA256(message, hmac_key).hexdigest()
```

`request_body` должен быть фактической строкой тела запроса, которая будет отправлена. Если это GET-запрос без тела, используйте пустую строку `""`.

Пример на Python:

```python
import hashlib
import hmac
import json
import time
import uuid

appid = "XC-A3BK7NMG"
hmac_key = "your_hmac_key"

payload = {
    "out_no": "order-001",
    "title": "Premium Plan",
    "currency": "USD",
    "amount": "29.99",
}
body = json.dumps(payload, separators=(",", ":"), ensure_ascii=False)
timestamp = str(int(time.time()))
nonce = str(uuid.uuid4())
signature = hmac.new(
    hmac_key.encode(),
    f"{nonce}{timestamp}{body}".encode(),
    hashlib.sha256,
).hexdigest()

headers = {
    "XC-Appid": appid,
    "XC-Timestamp": timestamp,
    "XC-Nonce": nonce,
    "XC-Signature": signature,
    "Content-Type": "application/json",
}
```

Пример на Node.js:

```javascript
const crypto = require("crypto");

const appid = "XC-A3BK7NMG";
const hmacKey = "your_hmac_key";
const body = JSON.stringify({
  out_no: "order-001",
  title: "Premium Plan",
  currency: "USD",
  amount: "29.99",
});
const timestamp = Math.floor(Date.now() / 1000).toString();
const nonce = crypto.randomUUID();
const signature = crypto
  .createHmac("sha256", hmacKey)
  .update(`${nonce}${timestamp}${body}`)
  .digest("hex");
```

## Формат ответа

При успехе напрямую возвращается бизнес-JSON. Интерфейсы создания обычно возвращают HTTP `201`, интерфейсы запросов (чтения) возвращают HTTP `200`.

Ошибки бизнес-логики:

```json
{
  "code": "1001",
  "message": "AppID无效",
  "detail": ""
}
```

Ошибки уровня фреймворка (например, несуществующий ресурс `404`, неверный метод запроса `405`, ограничение скорости `429`) могут возвращаться в формате DRF по умолчанию:

```json
{
  "detail": "Not found."
}
```

## Создание счета на оплату

`POST /v1/invoice`

Создает счет на оплату. При успешном создании возвращается `pay_url`, покупатель открывает эту страницу оплаты, выбирает валюту, сеть и совершает платеж.

### Параметры запроса

| Поле | Тип | Обяз. | Описание |
|------|------|------|------|
| `out_no` | string | Да | Номер заказа мерчанта, до 32 символов, уникальный в рамках проекта |
| `title` | string | Да | Заголовок счета, до 32 символов |
| `currency` | string | Да | Код фиатной валюты для оценки (например `USD`, `CNY`), должен поддерживаться системой; криптовалюта для оплаты определяется через `methods` |
| `amount` | string | Да | Сумма (в фиате), диапазон от `0.00000001` до `1000000` |
| `duration` | integer | Нет | Срок действия в минутах, от `5` до `30`, по умолчанию `10` |
| `methods` | object | Нет | Ограничение способов оплаты счета, формат `{"Валюта": ["код_сети"]}` |
| `notify_url` | string | Нет | Webhook-адрес уровня счета, имеет приоритет над адресом уведомлений проекта по умолчанию |
| `return_url` | string | Нет | URL синхронного возврата (редиректа) после завершения оплаты |

### Правила генерации methods

`methods` служит ограничивающим условием для доступных способов оплаты проекта:

- Не передано `methods`: система генерирует комбинации сетей и валют на основе настроек проекта.
- Передано `methods`: должно быть подмножеством системно сгенерированных комбинаций, иначе вернется ошибка отсутствия доступных способов оплаты.
- `currency` определяет только расчетную единицу (фиат) для `amount`, и отделена от криптовалюты, которую фактически платит покупатель — последняя ограничивается через `methods`.
- Конечные сеть, криптовалюта, адрес и сумма, которые должен оплатить покупатель, берутся из полей `chain`, `crypto`, `pay_address`, `pay_amount`, возвращаемых страницей/API оплаты; не пытайтесь самостоятельно вычислять сумму в крипте (on-chain) на основе `amount`.
- Символ `crypto` пишется в верхнем регистре (uppercase), код `chain` пишется в нижнем регистре (как в таблице выше).

### Режимы сбора и поддержка сетей

- Сбор счетов поддерживает два режима в зависимости от типа сети: Прямой сбор на кошелек (Differ) и Сбор через смарт-контракт (VaultSlot).
- В режиме прямого сбора на кошелек система использует настроенный адрес проекта и может незначительно менять `pay_amount` для различия счетов на одном адресе.
- В режиме сбора через смарт-контракт система выделяет адрес VaultSlot для счета; после подтверждения инициируется автоматический свипинг (сбор средств), и средства попадают на указанный адрес сбора проекта.
- И EVM, и Tron могут использоваться для сбора счетов; фактические комбинации зависят от статуса включения, связи валют в сети, режима сбора проекта и настройки адреса сбора.
- Адреса сбора для EVM должны быть в формате checksum (учитывать регистр), адреса Tron должны быть в формате Base58.
- При использовании смарт-контракта системный кошелек должен иметь небольшой баланс Gas / Energy в соответствующей сети для деплоя контрактов и транзакций сбора.

### Примеры запросов

```json
{
  "out_no": "order-20260602-001",
  "title": "Premium Plan",
  "currency": "USD",
  "amount": "29.99",
  "duration": 15,
  "methods": {
    "USDT": ["ethereum"],
    "USDC": ["base"]
  },
  "notify_url": "https://merchant.example.com/xcash/webhook",

```

Пример ограничения покупателя определенным стейблкоином (оценка в USD + USDT в `methods`). Фактическая сумма on-chain оплаты все равно определяется полем `pay_amount`:


Если в итоге остается только одна комбинация (один способ оплаты), система автоматически выберет его при создании, и тогда `chain`, `crypto`, `pay_address`, `pay_amount` могут быть сразу заполнены в ответе.

### Ограничение скорости (Rate Limit)

По умолчанию для анонимных запросов: `256/minute`.

## Запрос счета на оплату

`GET /v1/invoice/{sys_no}`

Публичный интерфейс, подпись не требуется. Используется на странице оплаты или на стороне покупателя для поллинга статуса счета. Не возвращает `appid`, `out_no`, `notify_url`.

### Поля ответа

| Поле | Тип | Описание |
|------|------|------|
| `sys_no` | string | Системный номер счета; формат: префикс + 6 цифр даты (ГГММДД) + 8 заглавных букв и цифр. Префикс счетов `INV`, префикс депозитов `DXC` |
| `title` | string | Заголовок |
| `currency` | string | Валюта оценки (фиат) |
| `amount` | string | Сумма оценки |
| `methods` | object | Доступные способы оплаты |
| `chain` | string \| null | Выбранная сеть |
| `crypto` | string \| null | Выбранная криптовалюта |
| `crypto_address` | string \| null | Адрес смарт-контракта токена в этой сети; для токенов газа обычно пусто (null) |
| `pay_address` | string \| null | Адрес для оплаты счета |
| `pay_amount` | string \| null | Сумма в криптовалюте, подлежащая оплате покупателем |
| `pay_url` | string | URL страницы оплаты |
| `started_at` | string | Время создания счета; при смене способа оплаты обновляется до времени выдачи текущих инструкций оплаты |
| `created_at` | string | Время создания |
| `expires_at` | string | Время истечения (срок действия) |
| `return_url` | string \| null | URL синхронного редиректа |
| `payment` | object \| null | Найденная on-chain транзакция |
| `payment_uri` | string \| null | Платежный URI EIP-681 (для EVM сетей); пусто для не-EVM или если сумму нельзя точно закодировать |
| `status` | string | Статус: `waiting` (ожидание) / `completed` (завершено) / `expired` (истекло) |
| `risk_level` | string \| null | Уровень риска |
| `risk_score` | string \| null | Оценка риска (скоринг) |

Поля объекта `payment`:

| Поле | Тип | Описание |
|------|------|------|
| `chain` | string | Код сети |
| `block` | integer | Номер блока |
| `hash` | string | Хэш транзакции (TxID) |
| `from_address` | string | Адрес отправителя |
| `to_address` | string | Адрес получателя |
| `crypto` | string | Криптовалюта |
| `amount` | string | Зачисленная сумма |
| `datetime` | string | Время транзакции |
| `status` | string | Статус перевода |
| `confirm_progress` | object | Прогресс подтверждений, включает `has_confirmed_count`, `need_confirmed_count`, `progress` |

### Ограничение скорости

`60/minute`, по параметрам `sys_no + IP`.

## Получение адреса для депозита

`GET /v1/deposit/address`

Требуется HMAC-подпись. Получение адреса депозита для конечных пользователей проекта. Для одного и того же проекта, одного `uid` и одной сети всегда возвращается один и тот же адрес смарт-контракта для депозитов.

### Параметры запроса (Query)

| Поле | Тип | Обяз. | Описание |
|------|------|------|------|
| `uid` | string | Да | Идентификатор конечного пользователя, от 1 до 128 символов, разрешены только буквы, цифры, подчеркивания и дефисы |
| `chain` | string | Да | Код сети, например `ethereum`, `base`, `tron` |
| `crypto` | string | Да | Символ валюты, например `USDT` |

Пример запроса:

```text
GET /v1/deposit/address?uid=user-10001&chain=base&crypto=USDC
```

При подписи GET-запроса `request_body` является пустой строкой `""`.

Пример ответа:

```json
{
  "deposit_address": "0xAbCd1234..."
}
```

Примечания:

- В настоящее время интерфейс депозитных адресов поддерживает EVM и Tron; для Tron в данный момент доступны USDT и нативный TRX.
- Запрашиваемая сеть, криптовалюта и их связь on-chain должны быть включены, а свойство проекта (testnet/mainnet) должно совпадать с сетью.
- После подтверждения депозита система инициирует сбор средств через смарт-контракт; системный кошелек должен иметь небольшой баланс Gas в соответствующей сети.

### Ограничение скорости

`60/minute`, по параметрам `appid + IP`.

## Webhook-колбэки (Уведомления)

Xcash отправляет Webhook мерчанту, когда счет или депозит переходит в ключевое состояние.

### Адрес доставки (URL)

- События счетов по нативному протоколу Xcash: приоритетно используется `notify_url`, переданный при создании счета, если он пуст — используется URL уведомлений проекта по умолчанию.
- События депозитов: используется URL уведомлений проекта по умолчанию.
- Заказы EPay V1: используется `notify_url` из параметров заказа EPay, уведомление доставляется GET-запросом по протоколу EPay.

В продакшен-среде по умолчанию разрешена доставка только на публичные HTTPS-адреса, отклоняются `http`, `localhost` и адреса из частных подсетей.

### Подпись Xcash Webhook

События счетов и депозитов по нативному протоколу Xcash используют `POST application/json` с заголовками HMAC:

```http
XC-Appid: {appid}
XC-Nonce: {event_nonce}
XC-Timestamp: {unix_timestamp}
XC-Signature: {hmac_signature}
Content-Type: application/json
```

Алгоритм подписи аналогичен запросам API:

```text
message   = XC-Nonce + XC-Timestamp + request_body
signature = HMAC-SHA256(message, hmac_key).hexdigest()
```

Мерчант должен проверять подпись и обеспечивать идемпотентную обработку для одинаковых `XC-Nonce`.

### Ответы и повторные попытки (Retry)

- Успешный ответ на Xcash Webhook: HTTP `200`, тело ответа без начальных/конечных пробелов равно `ok`.
- Успешный ответ на уведомление EPay V1: HTTP `200`, тело ответа без начальных/конечных пробелов равно `success`.
- Таймаут одиночного HTTP-запроса составляет 5 секунд.
- Повторные попытки с экспоненциальной задержкой выполняются только при сетевых ошибках или кодах 5xx; при 2xx (кроме 200), 3xx и 4xx повторных попыток нет.
- Переключатель уведомлений проекта должен быть включен; даже если передан отдельный `notify_url`, уведомление не будет доставлено, если уведомления проекта отключены.

### Webhook счетов на оплату

Логика триггера: уведомление отправляется один раз, когда счет переходит в статус `completed`, при этом `confirmed=true`.

Пример:

```json
{
  "type": "invoice",
  "data": {
    "sys_no": "INV2606028X7K2P9Q",
    "out_no": "order-20260602-001",
    "crypto": "USDT",
    "chain": "ethereum",
    "pay_address": "0xAbCd1234...",
    "pay_amount": "29.870001",
    "hash": "0xabc123...",
    "block": 12345678,
    "confirmed": true,
    "risk_level": null,
    "risk_score": null
  }
}
```

### Webhook депозитов

Логика триггера: уведомление отправляется один раз, когда on-chain транзакция депозита достигает требуемого числа подтверждений, при этом `confirmed=true`.

`risk_level` и `risk_score` — это снимок (snapshot) рисков на момент отправки уведомления; поскольку AML-проверка выполняется асинхронно, эти поля могут временно быть `null`. Не рассматривайте первый Webhook как окончательный отчет по рискам.

Пример:

```json
{
  "type": "deposit",
  "data": {
    "sys_no": "DXC2606026K9P2QWX",
    "uid": "user-10001",
    "chain": "base",
    "block": 12345678,
    "hash": "0xabc123...",
    "crypto": "USDC",
    "amount": "500",
    "confirmed": true,
    "risk_level": null,
    "risk_score": null
  }
}
```

## Совместимость с EasyPay V1

Xcash предоставляет совместимую точку входа EasyPay V1, подходящую для популярных плагинов EasyPay (Typecho, WordPress, Discuz и др.).

### Идентификация мерчанта

Проекты, созданные через Xcash SaaS, автоматически получают учетные данные мерчанта EPay; для самостоятельно развернутых или созданных вручную проектов убедитесь, что конфигурация EPay существует и включена в админ-панели:

| Поле | Описание |
|------|------|
| `pid` | ID мерчанта EPay |
| `secret_key` | Ключ MD5-подписи EPay |
| `active` | Включен ли вход EPay |

Можно просмотреть и изменить в блоке настроек EPay на странице проекта в панели администратора.

### Создание заказа

`GET /epay/submit.php` или `POST /epay/submit.php`

Точка входа EPay не использует заголовки HMAC Xcash, а использует собственную MD5-подпись EPay. Запросы `POST` должны использовать кодировку `application/x-www-form-urlencoded` или `multipart/form-data`; не отправляйте JSON.

| Поле | Тип | Обяз. | Описание |
|------|------|------|------|
| `pid` | integer | Да | ID мерчанта EPay |
| `type` | string | Нет | Совместимое с EPay поле, до 32 символов; Xcash не использует это поле для ограничения сетей или криптовалют, оно просто возвращается "как есть" в уведомлении |
| `out_trade_no` | string | Да | Номер заказа мерчанта, до 64 символов, уникальный для одного мерчанта EPay |
| `notify_url` | string | Да | Адрес асинхронного уведомления EPay |
| `return_url` | string | Нет | URL синхронного возврата |
| `name` | string | Да | Название товара, до 128 символов |
| `money` | string | Да | Сумма, минимум `0.01`, до двух знаков после запятой |
| `currency` | string | Нет | Расширенное поле Xcash, по умолчанию `CNY`; при передаче должен быть поддерживаемый системой код фиатной валюты |
| `param` | string | Нет | Дополнительный бизнес-параметр, до 512 символов |
| `sign` | string | Да | Подпись MD5 |
| `sign_type` | string | Да | Фиксированно `MD5` |

Заказы EPay создаются в соответствии с режимом сбора счетов проекта со сроком действия 15 минут. Повторная отправка с тем же `out_trade_no` и полностью идентичными метаданными вернет тот же самый счет; при расхождении метаданных вернется ошибка.

### Подпись EPay

1. Удалить `sign`, `sign_type`.
2. Удалить поля со значениями `null` или пустыми строками.
3. Отсортировать поля по именам в порядке возрастания ASCII.
4. Объединить как `key=value`, разделяя поля символом `&`.
5. В самый конец строки добавить `secret_key` (без `&`).
6. Вычислить MD5 полученной строки, вывести в нижнем регистре hex.

Пример на Python:

```python
import hashlib

params = {
    "pid": "1001",
    "out_trade_no": "order-001",
    "notify_url": "https://merchant.example.com/epay/notify",
    "return_url": "https://merchant.example.com/epay/return",
    "name": "Premium Plan",
    "money": "29.99",
    "sign_type": "MD5",
}

filtered = {
    k: str(v)
    for k, v in params.items()
    if k not in {"sign", "sign_type"} and v not in (None, "")
}
sign_string = "&".join(f"{k}={v}" for k, v in sorted(filtered.items()))
secret_key = "your_epay_secret_key"
params["sign"] = hashlib.md5(
    f"{sign_string}{secret_key}".encode("utf-8"),
    usedforsecurity=False,
).hexdigest()
```

### Ответ на создание

- Успех: HTTP `302`, редирект на страницу оплаты Xcash `/pay/{sys_no}`.
- Ошибка: HTTP `400`, простой текст `fail`.
- При срабатывании лимитов (rate limit) может возвращаться HTTP `429`.

### Асинхронное уведомление EPay

После завершения оплаты счета Xcash отправляет GET-запрос на `notify_url`, строка запроса (query string) включает:

| Поле | Описание |
|------|------|
| `pid` | ID мерчанта EPay |
| `trade_no` | Системный номер заказа Xcash |
| `out_trade_no` | Номер заказа мерчанта |
| `type` | Совместимое с EPay поле |
| `name` | Название товара |
| `money` | Сумма заказа, два знака после запятой |
| `trade_status` | Фиксированное значение `TRADE_SUCCESS` |
| `param` | Переданный при создании заказа расширенный параметр (возвращается, если есть) |
| `sign_type` | Фиксированно `MD5` |
| `sign` | Подпись MD5 EPay |

Если мерчант отвечает HTTP `200` с телом `success`, уведомление считается успешным.

### Синхронный редирект (Return)

После завершения оплаты, если при создании заказа EPay был передан `return_url`, публичный интерфейс запроса счета будет возвращать URL синхронного возврата с параметрами EPay и подписью. Синхронный возврат означает только окончание UI-процесса на странице оплаты, основная логика выдачи товара должна основываться на асинхронном уведомлении (Webhook).

## Полный цикл (Workflow)

### Оплата счетов

```text
Сервер мерчанта -> Xcash: POST /v1/invoice
Xcash -> Сервер мерчанта: Возвращает sys_no / pay_url
Покупатель -> Xcash: Открывает pay_url, выбирает валюту/сеть
Покупатель -> Блокчейн: Переводит средства
Xcash -> Сервер мерчанта: Webhook invoice
Сервер мерчанта -> Xcash: ok
```

### Депозиты

```text
Сервер мерчанта -> Xcash: GET /v1/deposit/address
Xcash -> Сервер мерчанта: Возвращает deposit_address
Система мерчанта -> Пользователь: Показывает deposit_address
Пользователь -> Блокчейн: Переводит средства
Xcash -> Сервер мерчанта: Webhook deposit
Сервер мерчанта -> Xcash: ok
```
