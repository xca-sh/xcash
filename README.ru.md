## Почему Xcash?

Хостинговые процессоры криптоплатежей берут ваши средства на хранение, взимают процент с каждой транзакции, требуют KYC и могут заморозить ваш аккаунт. Xcash работает на вашем собственном сервере, а деньги никогда не перестают быть вашими.

- **Некастодиальный** — платежи проходят через смарт-контракты напрямую на ваш адрес сбора. Система не хранит бизнес-средства, и даже взломанный сервер не может изменить, куда уходят деньги.
- **Нулевая комиссия платформы** — никакого процента при самостоятельном размещении. Вы платите только за газ в сети, а пакетная сборка средств удерживает его на низком уровне.
- **Стейблкоины в приоритете, мульти-сеть** — любой ERC-20 на Ethereum, BNB Chain, Arbitrum, Base, Polygon, Optimism и других EVM-сетях; USDT и TRX на Tron.
- **Два режима приёма в одной системе** — оплата счетов для чекаутов и подписок, плюс выделенные депозитные адреса в стиле биржи для платформ, ведущих балансы пользователей.
- **Готов к продакшену из коробки** — изоляция мерчантов и проектов, опциональная проверка рисков MistTrack, надёжные вебхуки, REST API с подписью HMAC, совместимость с EasyPay V1, развёртывание одной командой через Docker.

## Быстрый старт

Запустите продакшен-шлюз за несколько минут. Вам потребуется Linux-сервер с Docker и домен, направленный на него:

```bash
git clone https://github.com/xca-sh/xcash.git
cd xcash
./scripts/init_env.sh    # создаёт .env со случайными секретами
# отредактируйте .env и задайте SITE_DOMAIN=pay.example.com
docker compose up -d
```

Встроенный Caddy слушает `127.0.0.1:6688`; направьте на него свой обратный прокси (Nginx, Caddy, …) для TLS. При первом запуске создаётся учётная запись администратора `admin` с паролем, случайно сгенерированным `init_env.sh`: скрипт выводит его один раз и сохраняет в `.env` как `DJANGO_DEFAULT_SUPERUSER_PASSWORD`, поэтому **сохраните его в менеджер паролей**. Затем в админ-панели:

1. Укажите RPC-эндпоинты нужных сетей (QuickNode / Alchemy / Infura; для Tron — API-ключ TronGrid) и включите их.
2. Пополните системный кошелёк небольшим количеством газа в каждой включённой сети (для Tron нужна энергия).
3. Создайте проект, задайте адреса приёма и подключитесь через [REST API](API.ru.md).

Все шаги описаны в [руководстве по развёртыванию](#руководство-по-развёртыванию) ниже; принцип работы и расширенная настройка — на [xca.sh/docs](https://xca.sh/docs/).

> Не хотите обслуживать серверы? **[xca.sh](https://xca.sh)** — официальное облачное решение: первые $500 ежемесячного оборота без комиссии.

## Два способа принимать оплату

- **Оплата счетов** — для каждой транзакции создаётся счёт с фиксированной суммой и ограниченным сроком, который завершается после оплаты покупателем. Идеально для оформления заказов в интернет-магазинах и подписок. Поддерживаются прямой приём на кошелёк и приём через смарт-контракт; в комплекте — страница оплаты для покупателя на китайском, английском и русском языках.
- **Депозиты** — каждый пользователь получает выделенный депозитный адрес. Пользователи переводят средства когда угодно и получают зачисление после подтверждения блока, без создания заказа. Идеально для кошельков, торговых платформ и любого бизнеса, ведущего балансы пользователей.

## AML-проверка рисков (опционально)

Xcash может подключаться к оценкам риска адресов [MistTrack](https://misttrack.io/) (через дополнение MistTrack Address Risk Scores в QuickNode) для AML-проверки **адреса отправителя** каждого платежа:

- **Переключатель на уровне проекта** — каждый проект сам решает, включать ли проверку, и задаёт свой *порог AML-запросов* (по умолчанию 100 USD); запрос выполняется только для счетов и депозитов выше порога, что держит расходы на проверки под контролем.
- **Работает параллельно с подтверждением** — запрос стартует сразу после сопоставления перевода со счётом или депозитом и никогда не замедляет подтверждение; результат передаётся в вебхуке как `risk_level` (`Low` / `Moderate` / `High` / `Severe`) и `risk_score`, а в админ-панели счета и депозиты можно фильтровать по уровню риска.
- **Живой запрос для каждого платежа** — оценки адресов никогда не кэшируются, поэтому злоумышленник не может сначала «очистить» адрес легальными средствами, а затем заплатить грязными.
- **Только оценивает, никогда не блокирует** — средства поступают через контракт прямо на кошелёк мерчанта, поэтому система не может и не будет их отклонять. Результат проверки никогда не влияет на подтверждение, сбор средств и уведомления; **мерчант сам решает по уровню и оценке риска, отгружать ли товар, зачислять, замораживать или возвращать средства**.

Для платежей, не прошедших условия (проверка выключена, сумма не выше порога, небольшие счета с быстрым подтверждением, неподдерживаемые сети вроде тестовых, неудачный запрос), поля риска равны `null` — и `null` не означает низкий риск. Как включить проверку и что означает каждое поле — см. [API.ru.md · AML-контроль рисков](API.ru.md#aml-контроль-рисков).

## Руководство по развёртыванию

### Требования

- Linux-сервер, рекомендуется Ubuntu 22.04+ или Debian 12+
- Docker и Docker Compose
- Домен, направленный на IP сервера
- RPC-эндпоинты для сетей, которые вы хотите включить; API-ключ TronGrid для Tron

Рекомендуемые конфигурации сервера (задаётся `PERFORMANCE` в `.env`, по умолчанию `low`):

| Режим производительности | Железо | Ёмкость EVM-сетей | Процессов Django |
|:-------:|:-------:|:-----------:|:----------------:|
| low | 1 CPU / 2 GB | 2 – 3 EVM-сети | 1 |
| medium | 4 CPU / 8 GB | 8 – 15 EVM-сетей | 2 |
| high | 8 CPU / 16 GB | 15 – 30 EVM-сетей | 4 |

В продакшене Gunicorn использует фиксированные 4 потока запросов на каждый процесс Django, что даёт 4 / 8 / 16 одновременных слотов для веб-запросов в зависимости от режима.
`PERFORMANCE` управляет только количеством процессов Django, которое можно переопределить через `GUNICORN_WORKERS`; количество потоков больше не настраивается.
Параллелизм бизнес-задач по умолчанию равен 16 независимо от режима. Переопределить его можно через `WORKER_CONCURRENCY` — как в продакшене, так и в разработке.
Это рекомендации по развёртыванию; реальная ёмкость зависит от времени ответа RPC, нагрузки запросов и ресурсов базы данных.

### 1. Получите код и сгенерируйте конфигурацию

```bash
git clone https://github.com/xca-sh/xcash.git
cd xcash
./scripts/init_env.sh
```

Скрипт создаёт `.env` со случайными секретами и паролем базы данных; существующий `.env` он не перезаписывает.

### 2. Настройте домен и обратный прокси

Отредактируйте `.env`, задав домен, и убедитесь, что его DNS указывает на сервер:

```env
SITE_DOMAIN=xcash.example.com
```

Перенаправьте трафик на `http://127.0.0.1:6688` с помощью Nginx или Caddy. **Обратный прокси обязан передавать реальный IP клиента и протокол запроса**, иначе белые списки IP мерчантов и ограничения частоты запросов перестанут работать.

**Nginx:**

```nginx
location / {
    proxy_pass http://127.0.0.1:6688;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

**Caddy** (передаёт нужные заголовки автоматически):

```caddyfile
xcash.example.com {
    reverse_proxy 127.0.0.1:6688
}
```

Рекомендуется задать `ADMIN_PATH`, чтобы перенести админ-панель на собственный путь (без него она находится в корне сайта):

```env
ADMIN_PATH=secure-admin
```

### 3. Запустите сервисы

```bash
docker compose up -d
```

Образ загружается из `ghcr.io/xca-sh/xcash`, миграции базы данных выполняются автоматически при запуске. При первом запуске создаётся администратор `admin` с паролем из `DJANGO_DEFAULT_SUPERUSER_PASSWORD` в `.env`; в продакшене пустой пароль, пароль короче 12 символов или значение-заглушка приводят к отказу в создании администратора и остановке запуска.

### 4. Настройте и включите сети

Войдите в админ-панель и откройте **Блокчейн → Сети**: укажите RPC-эндпоинт для каждой EVM-сети (рекомендуются [QuickNode](https://www.quicknode.com/), [Alchemy](https://www.alchemy.com/) или [Infura](https://www.infura.io/)) и API-ключ [TronGrid](https://www.trongrid.io/) для Tron, затем отметьте *Включено*.

### 5. Пополните системный кошелёк

Откройте **Система → Системный кошелек** и скопируйте адрес системного кошелька:

- **EVM-сети** — отправьте небольшое количество нативного актива (ETH, BNB, POL, …) на газ.
- **Tron** — обеспечьте энергию (например, застейкав TRX) и держите небольшой баланс TRX для пропускной способности (bandwidth).

Системный кошелёк оплачивает только системные операции, такие как развёртывание контрактов и сбор средств; не храните на нём бизнес-средства.

### 6. Настройте проект

Откройте **Проект → Список проектов** и создайте проект; у каждого проекта свои `App ID` и `HMAC-ключ`. Затем настройте:

- **Белый список IP** — IP серверов мерчанта, которым разрешено вызывать API; на время тестирования можно указать `*`, в продакшене сузьте список.
- **Адрес для уведомлений** — принимает события вебхуков.
- **Адреса приёма** — по умолчанию счета используют прямой приём на кошелёк, поэтому достаточно добавить собственный *прямой адрес кошелька* на странице проекта; для депозитов и счетов через смарт-контракт нужен *адрес сбора* для соответствующего типа сети (EVM / Tron), который **нельзя изменить после установки** — рекомендуется мультиподписной кошелёк.

Проект готов к работе только после выполнения всех пунктов выше; иначе API возвращает `1004`. Далее следуйте [документации API](https://xca.sh/docs/#api-base) или [API.ru.md](API.ru.md), чтобы подключить платежи, депозиты и вебхуки.

Чтобы использовать [AML-проверку рисков](#aml-проверка-рисков-опционально), сначала укажите эндпоинт QuickNode с дополнением MistTrack Address Risk Scores в разделе **Система → Параметры работы → AML-проверка**, затем включите её и задайте порог запросов на вкладке *AML-проверка* на странице проекта.

## Резервное копирование и восстановление

Ключ, шифрующий мнемоники кошельков, хранится в `.env` как `WALLET_MNEMONIC_ENCRYPTION_KEY`, а не в базе данных. **Базу данных и `.env` нужно резервировать вместе** — ни одно из них по отдельности не позволит восстановить кошелёк.

Резервная копия базы данных (не реже раза в день, зашифрованная вместе с `.env` и хранящаяся вне этого сервера):

```bash
docker compose exec -T db sh -c 'pg_dump --format=custom --no-owner --no-privileges -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > xcash-$(date +%Y%m%d-%H%M%S).dump
```

Восстановление:

```bash
# 1. Остановите сервисы приложения, оставив базу данных запущенной
docker compose stop django worker chain-runner

# 2. Верните .env на место (это должна быть копия, соответствующая дампу)

# 3. Загрузите дамп (целевая база данных должна быть пустой)
docker compose exec -T db sh -c 'pg_restore --exit-on-error --no-owner --no-privileges -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < xcash-YYYYmmdd-HHMMSS.dump

# 4. Снова запустите сервисы
docker compose up -d
```

## Эксплуатация

```bash
docker compose ps        # показать состояние сервисов
docker compose down      # остановить сервисы (тома базы данных сохраняются)
```

Обновление до последней версии (убедитесь, что вы на ветке `main`):

```bash
git pull && ./scripts/upgrade.sh
```

Скрипт загружает новый образ, выполняет миграции и перезапускает сервисы, сообщая об успехе только когда всё готово; при ошибке он завершается с ненулевым кодом и выводит подсказки по диагностике.

Всегда обновляйтесь этим скриптом, а не вручную через `docker compose up -d`: он останавливает старые процессы по порядку, переносит незавершённые задачи, оставленные предыдущей версией в Redis, и удаляет выведенные из эксплуатации сервисы через `--remove-orphans`. Особенно при обновлении с версии на Celery ручной `up -d` оставит старый beat работать как контейнер-сироту, который продолжит публиковать никем не потребляемые задачи, пока Redis не упрётся в лимит памяти.

Если вы не хотите самостоятельно разворачивать и обслуживать Xcash, используйте официальную облачную версию на **[xca.sh](https://xca.sh)** — без развёртывания, без обслуживания, с постоянными обновлениями.

Комиссия зависит от месячного оборота и начисляется по ступеням: **первые $500 каждый месяц бесплатно**, далее 1% → 0,8% → 0,6% → 0,4% по мере роста оборота. Самостоятельное размещение в любом случае остаётся бесплатным и без комиссии.
